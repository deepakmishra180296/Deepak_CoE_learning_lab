# Day 8 – CI/CD with GitHub Actions (Playwright Test Automation)

## 1. Overview of Day 8 Objectives

The goal of Day 8 is to set up an automated CI/CD pipeline using GitHub Actions to run Playwright tests automatically on every code push, split tests across parallel runners (test sharding), generate HTML test reports, and attach test traces as downloadable CI artifacts for debugging.

---

## 2. Repository Analysis

In this repository, the tests are split across two ecosystems:

| Test Suite | Location | Framework / Tools | How Tests are Executed |
| :--- | :--- | :--- | :--- |
| **Python Tests** | `python_exercises/` | `pytest`, `pytest-playwright`, `pytest-rerunfailures`, `pytest-html` | `pytest tests/` |
| **TypeScript Tests** | `typescript-exercises/greenkart-bdd/` | Cucumber BDD, `@playwright/test`, `tsx` | `npx cucumber-js` |

Both test suites use Playwright for browser interactions. Therefore, our GitHub Actions workflow includes jobs for both test suites.

---

## 3. Key Concepts Implemented

### 1. Triggering on Every Push
In GitHub Actions, workflows are triggered using the `on` block:
```yaml
on:
  push:
  workflow_dispatch:
```
- `push`: Automatically triggers the pipeline on every commit pushed to GitHub.
- `workflow_dispatch`: Enables manual "Run workflow" trigger from the GitHub Actions UI.

### 2. Test Sharding via GitHub Actions Matrix
Test sharding splits a test suite into smaller parts that run simultaneously on different virtual machines. This reduces total build time.
In GitHub Actions, sharding is achieved using `strategy.matrix`:
```yaml
strategy:
  fail-fast: false
  matrix:
    shard: [1, 2]
    include:
      - shard: 1
        test_files: "tests/test_isolation.py tests/test_string_calculator.py ..."
      - shard: 2
        test_files: "tests/test_retry.py tests/test_advance_ui_automation.py ..."
```
- Two runners launch simultaneously in parallel.
- `fail-fast: false`: Ensures that if Shard 1 fails, Shard 2 continues running and finishes its tests.

### 3. Generating HTML Reports
- **Python**: Generated by `pytest-html` via `--html=report.html --self-contained-html` configured in `python_exercises/pytest.ini`.
- **TypeScript**: Generated by Cucumber via `--format html:reports/cucumber-report.html` configured in `cucumber.js`.

### 4. Capturing Traces and Uploading CI Artifacts
- **Playwright Tracing on Failure**: Configured via `--tracing=retain-on-failure` in `pytest.ini` for Python, and via `tracing.start()` / `tracing.stop()` in `support/hooks.ts` for TypeScript.
- **Uploading Artifacts**: Uploaded using `actions/upload-artifact@v4`:
```yaml
- name: Upload Python Test Report and Traces
  uses: actions/upload-artifact@v4
  if: always()
  with:
    name: python-playwright-report-shard-${{ matrix.shard }}
    path: |
      python_exercises/report.html
      python_exercises/test-results/
    retention-days: 7
```
- `if: always()`: Ensures that the report and failure traces are uploaded even if a test fails.

## 4. Continuous Integration (CI) – Key Principles

**Summary:** CI is the practice of integrating small code changes frequently and checking them automatically, so problems are found early instead of accumulating until a large release.

- Commit and integrate changes regularly; smaller changes are usually easier to understand and troubleshoot.
- Automatically build and test each change to get quick, reliable feedback.
- Keep the pipeline fast and repeatable so developers do not avoid running it.
- Treat a broken build as a priority: identify the failure and restore a green pipeline before adding more changes.
- Make failures visible and actionable. A passing pipeline is useful only when its tests provide meaningful coverage.


## 5. Continuous Delivery vs. Continuous Deployment

**Summary:** Both practices automate the path from code change to a release-ready product. The main difference is whether production deployment still requires a separate decision.

- **Continuous Delivery:** The application is built, tested, and kept ready for release; a person or business process may decide when to deploy it to production.
- **Continuous Deployment:** Every change that passes the required automated checks is deployed to production automatically.
- **Continuous Integration** focuses on frequently merging changes and validating them; delivery/deployment extends the automation towards release.
- Automated tests, monitoring, and a safe recovery approach help teams release changes with confidence.

## 6. DORA – Five Software Delivery Metrics

**Summary:** DORA metrics help a team understand both the speed of software delivery and the stability of changes. They are most useful for tracking improvement over time for a specific application or service, not for ranking teams.

- **Change lead time:** How long a code change takes to move from version control commit to production.
- **Deployment frequency:** How often changes are deployed to production.
- **Failed deployment recovery time:** How long it takes to recover when a deployment fails and requires intervention.
- **Change fail rate:** The proportion of deployments that require immediate intervention, such as a rollback or hotfix.
- **Deployment rework rate:** The proportion of deployments that are unplanned and triggered by a production incident.

Use the metrics together, consider the context of the application, and look for trends. Avoid turning one metric into a target that encourages teams to game the numbers.

## 7. GitHub Actions – Workflow Files, Jobs, and Matrix Builds

**Summary:** GitHub Actions runs automated workflows in response to repository events. A workflow is a YAML file stored under `.github/workflows/`; it contains triggers, jobs, and steps.

- `on` defines the trigger, such as `push`, `pull_request`, or `workflow_dispatch` for a manual run.
- A **job** runs on a runner and contains ordered **steps** that execute commands or reusable actions.
- Use separate jobs when test suites have different dependencies. In this repository, Python/pytest and TypeScript/Cucumber are separate test ecosystems.
- `strategy.matrix` runs a job with different values or configurations, such as separate test groups or browser versions.
- Install the required language dependencies and Playwright browsers before running browser tests.

## 8. Parallel Test Execution and Sharding

**Summary:** Sharding divides a large test suite into smaller groups that run on separate CI jobs. This can reduce total pipeline time, although it uses more runner resources.

- With GitHub Actions, a matrix can create one job per shard and run those jobs in parallel.
- In the existing Python workflow, test files are assigned to different matrix shards. Keep the groups reasonably balanced so one slow shard does not delay the whole workflow.
- For Playwright Test in TypeScript, its built-in option is `--shard=<index>/<total>`, for example `--shard=1/4`.
- Keep tests independent; sharding exposes hidden dependencies when one test expects data or state created by another.


## 9. CI Test Reports, Traces, and Artifacts

**Summary:** Reports show the overall test result, while traces help investigate the actions and browser state around a failure. Uploading them as workflow artifacts makes the evidence available after the runner finishes.

- The Python suite uses `pytest-html` to create an HTML report; the TypeScript BDD suite creates a Cucumber HTML report.
- Configure Playwright tracing for failures or retries, then ensure the generated trace files are included in the artifact upload path.
- Use `actions/upload-artifact` to save reports and trace files; an `if: always()` condition can preserve diagnostic output even when tests fail.
- Open a trace with the Playwright Trace Viewer to step through recorded actions and inspect what happened during execution.

## 10. Environment Variables and Secrets in CI

**Summary:** Environment variables configure a workflow, while secrets store sensitive values such as passwords, tokens, and API keys. Both allow tests to run without hard-coding environment-specific values in source code.

- Define non-sensitive variables at workflow, job, or step level using `env`; keep values appropriate to each environment.
- Store credentials in GitHub Actions Secrets and reference them through the `secrets` context rather than writing them directly in YAML or committing a `.env` file.
- Give the workflow and `GITHUB_TOKEN` only the permissions they need; and not to print secrets in logs.
- Keep test configuration separate from test code and use different credentials for test/staging environments where applicable.

## 11. Reflection – GitHub Actions Compared with Jenkins

GitHub Actions fits naturally into a GitHub repository: workflow files are version-controlled alongside the code, and push or pull-request events can start the pipeline automatically. Jenkins supports similar stages, jobs, agents, test execution, and artifact handling, but commonly requires a separately managed controller and plugin configuration. GitHub-hosted runners reduce the need to maintain build machines, while Jenkins gives teams more control over their own infrastructure; GitHub Actions can also use self-hosted runners.

The concepts are largely the same in both systems: trigger the pipeline, prepare the environment, run checks, publish reports, protect credentials, and make failures visible.
